# 19 - What the sources say that the bubblewrap backend rests on

Recorded 2026-11-26, for issue #86: what the source and the manual of bubblewrap, the seccomp filter of Flatpak, the default seccomp profile of Moby and the crates `seccompiler` and `hyper` say on the points that the bubblewrap backend rests on (SPEC SEC-6e, SEC-10a, SEC-10b, D-40). Nothing here was run inside a sandbox. No filter was compiled, no process was started under bubblewrap and no connection was forwarded. What the backend does on a kernel is probe P-37.

Method: the session downloaded each file below on 2026-11-26 and read the lines it cites. Line numbers are those of the file at the named tag or commit. Section 6 holds the one thing that was run, `cargo tree` on a throwaway package. A statement marked **(inference)** is a reading and not something a file states.

## 1. How far to trust it

- **Two versions of bubblewrap were read**, 0.9.0 and 0.12.0: the version that apt installs on the hosted runners (P-16) and the version of the server and of the development VM (P-24, P-36). The lines cited are those of 0.9.0. For 0.12.0 the list of options in the manual and the signal handling in the source were compared and nothing else.
- **Flatpak and Moby were read at the head of their default branch**, not at a release. The commits are named below.
- **What a kernel does with any of it is not in a source file.** That a signal without a handler does not reach PID 1 of a PID namespace, and that a filter is inherited over `execve`, is this session's knowledge of Linux and was not read anywhere on 2026-11-26.
- **Cargo's documentation of its proxy variables was not read.** The file was not found at the two paths tried. Which variables `cargo` reads is part of P-37.

## 2. bubblewrap

Files, from `https://github.com/containers/bubblewrap` at the tags `v0.9.0` and `v0.12.0`: `bwrap.xml` (the manual), `bubblewrap.c`, and `network.c` at `v0.9.0`.

| Point | What the file states |
|---|---|
| The options | Both manuals list `--seccomp`, `--add-seccomp-fd`, `--as-pid-1`, `--new-session`, `--die-with-parent`, `--info-fd`, `--json-status-fd`, `--disable-userns`, `--unshare-net`, `--size` and `--perms`. 0.12.0 adds `--level-prefix` and `--overlay-src` |
| The filter's form | `--seccomp FD`: "The rules need to be in the form of a compiled cBPF program, as generated by seccomp_export_bpf." The source reads the descriptor whole and dies where its length is no multiple of 8 bytes (`bubblewrap.c:276`), the size of one instruction |
| Several filters | `--add-seccomp-fd FD`: "This option can be repeated, in which case all the seccomp programs will be loaded in the order given (note that the kernel will evaluate them in reverse order, so the last program on the bwrap command-line is evaluated first). All of them, except possibly the last, must allow use of the PR_SET_SECCOMP prctl. This option cannot be combined with --seccomp." |
| When the filter is applied | In the process that becomes the command, as "the last thing before execve() so that filters don't need to handle anything above" (`bubblewrap.c:3367`), and in bubblewrap's own PID 1 where it has one (`bubblewrap.c:620`) |
| PID 1 | With `--unshare-pid` and without `--as-pid-1`, bubblewrap forks once more: the parent stays as PID 1 and reaps, the child becomes the command (`bubblewrap.c:3309`). `--as-pid-1`: "Do not create a process with PID=1 in the sandbox to reap child processes." It needs `--unshare-pid` (`bubblewrap.c:2810`) |
| The pid of the child | `--json-status-fd`: "After bwrap has started the child process inside the sandbox, it writes an object with a child-pid member [...] The corresponding value is the process ID of the child process in the pid namespace from which bwrap was run." With `--as-pid-1` that child is the command **(inference)** |
| Signals | The outer process waits on a `signalfd` that holds SIGCHLD alone (`bubblewrap.c:520`). The source touches SIGCHLD and no other signal: 0.9.0 blocks it for that `signalfd`, and 0.12.0 also sets its disposition back to the default (`bubblewrap.c:2879` there). So bubblewrap passes no signal on, and a SIGTERM ends its outer process **(inference)** |
| `--die-with-parent` | "Kills (SIGKILL) all bwrap sandbox processes in sequence from parent to child including COMMAND process when bwrap or bwrap's parent dies." The source sets `PR_SET_PDEATHSIG` to SIGKILL (`bubblewrap.c:380`) |
| `--new-session` | "Create a new terminal session for the sandbox (calls setsid()). This disconnects the sandbox from the controlling terminal [...] if you don't use --new-session, it is recommended to use seccomp to disallow the TIOCSTI ioctl, otherwise the application can feed keyboard input to the terminal which can e.g. lead to out-of-sandbox command execution (see CVE-2017-5226)." |
| Holding the child back | `--block-fd FD`: the child reads one byte from the descriptor before it goes on (`bubblewrap.c:3261`), which is after the outer process wrote `child-pid` **(inference)** |
| The loopback interface | With `--unshare-net` the source calls `loopback_setup` (`bubblewrap.c:3047`), which sets the flag `IFF_UP` on the interface `lo` (`network.c:150`, `192`) |
| `--disable-userns` | "This option requires --unshare-user." Observed as P-36 |
| A temporary file system | `--tmpfs DEST` has mode 0755 and the default size unless `--perms` or `--size` precedes it |

## 3. Flatpak's filter

File: `common/flatpak-run.c` of `https://github.com/flatpak/flatpak`, at commit `cea67024` of the branch `main` (2026-11-25); the file last changed in commit `a2bef85d` (2026-11-12). The function is `setup_seccomp`. Its comment calls Flatpak "the canonical upstream location for this code" and names WebKit and GNOME as projects that copy it.

The filter is built with `seccomp_init (SCMP_ACT_ALLOW)`: every call is allowed but those below.

| Refused | With | The source's comment |
|---|---|---|
| `syslog` | `EPERM` | "Block dmesg" |
| `uselib` | `EPERM` | "Useless old syscall" |
| `acct` | `EPERM` | "Don't allow disabling accounting" |
| `quotactl` | `EPERM` | "Don't allow reading current quota use" |
| `add_key`, `keyctl`, `request_key` | `EPERM` | "Don't allow access to the kernel keyring" |
| `move_pages`, `mbind`, `get_mempolicy`, `set_mempolicy`, `migrate_pages` | `EPERM` | "Scary VM/NUMA ops" |
| `unshare`, `setns`, `mount`, `umount`, `umount2`, `pivot_root`, `chroot` | `EPERM` | "Don't allow subnamespace setups" |
| `clone` where the first argument has `CLONE_NEWUSER` | `EPERM` | The same |
| `ioctl` where the low 32 bits of the second argument are `TIOCSTI` | `EPERM` | "Don't allow faking input to the controlling tty (CVE-2017-5226)" |
| `ioctl`, likewise, with `TIOCLINUX` | `EPERM` | "copy/paste operations have an effect similar to TIOCSTI (CVE-2023-28100)" |
| `clone3` | `ENOSYS` | "seccomp can't look into clone3()'s struct clone_args to check whether the flags are OK, so we have no choice but to block clone3(). Return ENOSYS so user-space will fall back to clone(). (CVE-2021-41133 [...])" |
| `open_tree`, `move_mount`, `fsopen`, `fsconfig`, `fsmount`, `fspick`, `mount_setattr` | `ENOSYS` | "New mount manipulation APIs can also change our VFS. There's no legitimate reason to do these in the sandbox" |
| `modify_ldt`, unless the run is multiarch | `EPERM` | "a historic source of interesting information leaks" |
| `perf_event_open`, unless the run is a development run | `EPERM` | "In particular perf has been the source of many CVEs" |
| `personality` with an argument other than the allowed one, unless a development run | `EPERM` | "Don't allow you to switch to bsd emulation or whatnot". The allowed value is `PER_LINUX`, or `PER_LINUX32` for a 32-bit runtime |
| `ptrace`, unless a development run | `EPERM` | None |
| `socket` with a family other than `AF_UNSPEC`, `AF_LOCAL`, `AF_INET`, `AF_INET6` and `AF_NETLINK` (and, with a flag each, `AF_CAN` and `AF_BLUETOOTH`) | `EAFNOSUPPORT` | "Blocklist all but unix, inet, inet6 and netlink" |

The filter is exported with `seccomp_export_bpf` and handed to bubblewrap with `--seccomp`.

## 4. Moby's default profile

File: `seccomp/default.json` of `https://github.com/moby/profiles`, at commit `a0fa7080` of the branch `main` (2026-11-20); the file last changed in commit `9ee3204f` (2026-11-10).

- **It is an allow-list.** `defaultAction` is `SCMP_ACT_ERRNO` with `defaultErrnoRet` 1, which is `EPERM`. One entry allows 359 calls by name without a condition. The other 61 entries allow a call under a condition: a kernel version, an architecture, a capability or an argument.
- **Its architectures.** For x86-64 the map names x86 and x32 as sub-architectures, and for arm64 the 32-bit `arm`.
- **`clone`** is allowed without `CAP_SYS_ADMIN` only where the first argument has none of the bits of the mask 2114060288, which is `0x7E020000`. Those bits are `CLONE_NEWNS`, `CLONE_NEWCGROUP`, `CLONE_NEWUTS`, `CLONE_NEWIPC`, `CLONE_NEWUSER`, `CLONE_NEWPID` and `CLONE_NEWNET` **(inference)**: the file gives the number and not the names. **`clone3`** gets `ENOSYS` (errno 38) without that capability.
- **Not allowed without a capability,** among others: `bpf`, `perf_event_open`, `mount` and the newer mount calls, `setns`, `unshare`, `syslog`, `quotactl`, `chroot`, `acct`, `kcmp`, `pidfd_getfd`, `process_madvise`, `mbind`, `get_mempolicy`, `set_mempolicy`. `ptrace`, `process_vm_readv` and `process_vm_writev` are allowed from kernel 4.8 on.
- **In no entry,** so refused: `io_uring_setup`, `io_uring_enter`, `io_uring_register`, `userfaultfd`, `keyctl`, `add_key`, `request_key`, `move_pages`, `migrate_pages`, `pivot_root`, `uselib`.
- **`socket`** is allowed for a list of families, by number. 38 and 40 are not on it, which are `AF_ALG` and `AF_VSOCK` **(inference)**.
- **`personality`** is allowed with five values, among them 0 and 4294967295, the value that asks for the current one.

## 5. `seccompiler`

Files: `Cargo.toml`, `README.md` and `src/lib.rs`, `src/backend/mod.rs`, `src/backend/bpf.rs`, `src/backend/filter.rs` of `https://github.com/rust-vmm/seccompiler` at the tag `v0.5.0`, the version current on crates.io on 2026-11-26.

| Point | What the file states |
|---|---|
| What it is | "Provides easy-to-use seccomp-bpf jailing", by the Firecracker team. Licence `Apache-2.0 OR BSD-3-Clause`. Its one dependency without a feature is `libc` |
| Platforms | "supported only on Linux systems", on little-endian x86-64, aarch64 and riscv64 |
| What it yields | `BpfProgram`, which is `Vec<sock_filter>`: the instructions that bubblewrap takes, 8 bytes each **(inference)** |
| A filter | `SeccompFilter::new(rules, mismatch_action, match_action, target_arch)`. `rules` maps a call number to its rules. A filter has one action for every call that matches and one for the rest, and the two must differ. So calls refused with different error codes need a filter each **(inference)** |
| Actions | `Allow`, `Errno(u32)`, `KillThread`, `KillProcess`, `Log`, `Trace(u32)`, `Trap` |
| Arguments | A rule compares arguments, with `MaskedEq(u64)` among the operators |
| The architecture | Every program begins by comparing the architecture of the call with the target's and returns `SECCOMP_RET_KILL_PROCESS` where they differ (`bpf.rs:73` to `78`). The constants are `AUDIT_ARCH_X86_64`, `AUDIT_ARCH_AARCH64` and `AUDIT_ARCH_RISCV64` |
| The x32 ABI | Not mentioned. A rule is keyed by one exact call number, so a filter cannot say "every number from `0x40000000`", which is how a call of that ABI arrives under the architecture of x86-64 **(inference)** |

## 6. What the crates resolve to

Run on 2026-11-26 on the operator's Mac with cargo 1.100.0: `cargo generate-lockfile` and `cargo tree --target x86_64-unknown-linux-gnu` in a throwaway package that depends on `axum` 0.8, `reqwest` 0.13, `tokio` 1 and, for Linux targets only, `seccompiler` 0.5.0.

- `axum` 0.8.9 and `reqwest` 0.13.5 resolved, with `hyper` 1.13.0, `hyper-util` 0.1.21, `http-body-util` 0.1.5 and `httparse` 1.10.1.
- `cargo tree -i hyper` names `axum` as a dependent, and `cargo tree -i hyper-util` names `axum`, `reqwest` and `hyper-rustls`. A crate that depends on `axum` therefore has both already.
- `seccompiler` 0.5.0 depends on `libc` and on nothing else. For the target `aarch64-apple-darwin` it is not in the tree.

## 7. `hyper`

Files: `src/proto/h1/role.rs` and `src/server/conn/http1.rs` of `hyper` 1.13.0, as cargo unpacked the crate for the package of section 6. A reviewer of the change for issue #86 pointed at them, and the session then read the lines.

- **A head that cannot be parsed is answered by `hyper`.** `Server::on_error` (`role.rs:493`) picks the status "for parse error" and sends it as an "automatic response": 400 for a bad method, header, URI or version, 431 for `Parse::TooLarge` and 414 for `Parse::UriTooLong`. For every other error it returns `None`, and nothing is sent. The service that the proxy hands to `hyper` is not called for such a head **(inference)**.
- **The cap on a head.** `max_buf_size`: "The minimum value allowed is 8192. This method panics if the passed `max` is less than the minimum." (`http1.rs:398`)
- **A slow head.** `header_read_timeout` has a default of 30 seconds. What a client gets when it runs out was not read beyond `on_error`, which names no timeout.

## 8. What the probe record already holds

- The harness of P-22 ran each session of the agent CLI behind a CONNECT proxy and set `HTTPS_PROXY`, `HTTP_PROXY`, `https_proxy` and `http_proxy` to its address (`lockdown_probe.py` on the branch `prototype/claude-code-lockdown`). That was on macOS and outside a sandbox, where a name resolves.
